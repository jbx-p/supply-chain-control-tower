\# GenAI Executive Briefing Approach — Phase 7



\## Overview

A pipeline that curates decision-relevant results from Phases 3-6 (demand forecasts, supplier risk scores, inventory optimization, disruption simulation) and uses an LLM to synthesize them into a structured, plain-language weekly executive briefing — grounded strictly in real computed numbers, not invented content.



\## Design principle: curation over dumping

The input to the model is a small, hand-selected summary (top 3 growing/declining products, top 5 riskiest suppliers, aggregate cost and service-level figures) rather than a raw dump of all 40 products' data. A briefing meant for a busy executive is only useful if it's actually brief — feeding the model everything and asking it to "summarize" produces a worse result than feeding it a pre-curated set of the most decision-relevant facts and asking it to explain them.



\## Prompt design

\- \*\*System prompt explicitly forbids inventing numbers not present in the input.\*\* This is the single most important instruction in the pipeline — without it, there's a real risk of plausible-sounding but fabricated figures. Every number in the output is traceable back to a real query result.

\- \*\*User prompt enforces a fixed 5-section structure\*\* (Headline, Demand Outlook, Supplier Risk Alerts, Inventory \& Cost, Resilience Check) and a 300-word limit, so the output is consistently scannable rather than open-ended.

\- \*\*Explicit instruction to state tradeoffs honestly\*\* (e.g., a cost increase isn't hidden behind only positive framing) — this was deliberate, matching the project's overall approach of reporting findings honestly rather than only the flattering version (consistent with how Phases 5 and 6 were documented).



\## A real pivot during development: Anthropic → OpenRouter

This phase was originally built directly against the Anthropic API (`anthropic` Python SDK, `client.messages.create`). During development, the Anthropic account hit a billing block (a declined card charge when attempting to add API credits). Rather than stall the project, the integration was switched to \*\*OpenRouter\*\*, which provides OpenAI-compatible access to the same Claude models. This required:

\- Swapping the `anthropic` client for `openai.OpenAI(base\_url="https://openrouter.ai/api/v1", ...)`

\- Moving the system prompt from a dedicated `system=` parameter into the `messages` list as a `{"role": "system", ...}` entry (Anthropic's SDK and the OpenAI-compatible format structure this differently)

\- Reading the response from `response.choices\[0].message.content` instead of `response.content\[0].text`

\- Using OpenRouter's `provider/model` naming convention (`anthropic/claude-sonnet-4.5`)



This is worth being upfront about rather than hiding: the underlying model (Claude) and prompt design are unchanged, only the API routing layer differs. It's also a legitimate demonstration of adapting a pipeline to a real operational constraint rather than the tooling being fixed in stone.



\## Example output

Below is a real, unedited briefing generated by the pipeline from the project's actual Phase 3-6 results:



> \*\*Headline\*\*

> Apparel demand is surging 20% while electronics decline sharply, but two high-risk suppliers (Munoz-Roman and Arnold Ltd) require immediate attention.

>

> \*\*Demand Outlook\*\*

> Apparel products P005, P026, and P033 are growing 19-20%, while electronics products P025, P021, and P001 are declining 20-22%. Our forecast accuracy is solid at 13.5% error, giving us reasonable confidence to adjust production and inventory plans accordingly.

>

> \*\*Supplier Risk Alerts\*\*

> Munoz-Roman (Saint Lucia, risk score 87.3) and Arnold Ltd (Niger, risk score 82.9) are both high-risk and need contingency plans — consider dual-sourcing or building buffer stock for products they supply. Peterson-Moore (Serbia) and Herrera-Dudley (Honduras) are medium-risk but stable enough to monitor without immediate action.

>

> \*\*Inventory \& Cost\*\*

> The optimized inventory policy costs $7.2M versus $6.3M for our current approach — a 15.3% increase ($956K more). This isn't waste: we're paying for resilience. The higher cost buys us better service levels during disruptions, particularly for high-demand apparel products.

>

> \*\*Resilience Check\*\*

> Disruption simulations show the optimized policy maintains 92.2% service levels versus 92.0% under current practices — a modest gain overall, but products P015, P009, and P005 see meaningful protection (up to 2.7 percentage points better). Given the volatile supplier landscape and demand shifts, this stability is worth the premium.



\## Accuracy verification

Every figure in this example was spot-checked against its source table:

\- 92.2% / 92.0% service levels — matches `simulation\_policy\_comparison` (92.24% / 91.97%) ✅

\- $7.2M / $6.3M / 15.3% — matches `optimization\_vs\_naive\_comparison` exactly ✅

\- Munoz-Roman (87.3) / Arnold Ltd (82.9) — matches `supplier\_risk\_scores` top-2 exactly ✅

\- P015/P009/P005 as top resilience gainers — matches Phase 6's `service\_level\_improvement` ranking ✅



No fabricated or unsupported figures were found in this output — the grounding instruction in the system prompt is working as intended.



\## Output

Briefings are saved to `reports/executive\_briefing\_<date>.md`, designed to be re-run on a schedule (e.g. weekly, via a cron job or scheduled GitHub Action) to produce a fresh briefing as underlying data updates — not built as a fully automated schedule in this phase, but the code is structured to support it directly.
